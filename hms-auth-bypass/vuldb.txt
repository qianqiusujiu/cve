Title
Hospital-Management-System SQL Injection Authentication Bypass (vanilla PHP + MySQLi)

Vendor
kishan0725

Product
Hospital-Management-System (vanilla PHP + MySQLi)

Version
n/a (master branch, commit 777fda46b77a820977a5ba616283dbfbc40bf7e1, last commit 2024-10-07; no official release version)

Class
CWE-89: Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection') (CWE-89)

Description
Hospital-Management-System (github.com/kishan0725/Hospital-Management-System) is a hospital management web application written in plain PHP with a MySQLi backend; the project ships a seeded database (myhmsdb.sql) that stores patient and doctor accounts, including plaintext passwords.

Both interactive login handlers build their SQL statement by raw string concatenation of unfiltered POST input and pass it to mysqli_query:
- Patient login, func.php lines 8-10: select * from patreg where email='$email' and password='$password'; built from $_POST['email'] and $_POST['password2'] (submitted as patsub=1).
- Doctor login, func1.php lines 7-9: select * from doctb where username='$dname' and password='$dpass'; built from $_POST['username3'] and $_POST['password3'] (submitted as docsub1=1).

No authentication is required to reach either endpoint; the flat file layout makes both handlers directly POSTable.

Authentication bypass: submitting email=' OR 1=1 LIMIT 1# together with an arbitrary password to the patient login tautologizes the WHERE clause; LIMIT 1 guarantees exactly one result row, which satisfies the mysqli_num_rows()==1 check. The handler then populates $_SESSION['pid'], $_SESSION['username'] and $_SESSION['email'] from that row and issues a 302 redirect to admin-panel.php. Verified against a local instance (MySQL 8.0.39, PHP 8.4.26, display_errors=0, seeded myhmsdb.sql): the server answered HTTP 302 with a session cookie, and a subsequent GET /admin-panel.php with that cookie rendered the authenticated patient dashboard of the first patreg row (welcome banner with that row's first name and last name, pid=1). The identical injection against the doctor login (username3=' OR 1=1 LIMIT 1#) returned HTTP 302 to doctor-panel.php, and the issued cookie rendered the authenticated doctor dashboard. Baseline submissions with a nonexistent account return the invalid-credentials alert in both handlers.

An unauthenticated attacker therefore obtains a fully privileged patient session and a fully privileged doctor session without any credential. Patient access exposes bookings, prescriptions and billing records; doctor access exposes appointments, prescriptions and patient data. The obtained session also chains into further flaws, e.g. the appointment-booking INSERT statement of the same project only evaluates with a patient session.

Fix: replace both login queries with prepared statements using bound parameters, and store only password_hash() digests verified with password_verify() (the schema currently stores plaintext passwords); add rate limiting on both handlers.
